# Architecture and invariants

## Components

Browser/PWA → HTTPS Caddy → FastAPI → PostgreSQL.

Redis supplies shared rate-limit counters. Uploaded photos are re-encoded as JPEG and stored on a persistent media volume. The optional push worker reads a PostgreSQL transactional outbox and delivers Web Push through browser vendors. Payment operations use Razorpay's server API and verified webhooks.

The frontend remains buildless HTML/CSS/JavaScript to preserve the delivered design and avoid unnecessary framework migration. The API uses Pydantic input schemas and SQLAlchemy models. Domain concerns are separated into models, schemas, session/security configuration, payment adapter, push queue, worker and operator commands. Routes are in `main.py`; split these into routers as the team and scope grow.

## Identity and access

- Passwords are hashed using Argon2; raw passwords are never stored.
- Login issues a cryptographically random opaque token. Only its SHA-256 digest is stored server-side.
- Cookies are HttpOnly, SameSite=Lax and Secure in production. Sessions expire after seven days.
- State-changing routes require the configured Origin and a custom request header. Webhooks use HMAC validation instead.
- A view switch is not a role grant. Every owner operation checks the authenticated owner against the property.
- Tenants cannot assign beds, change invoice amounts, resolve their own requests as the owner, or inspect other tenants' receipts.
- Email/password registration does not verify email or phone ownership. Tenant identity is checked by the owner before approval; property ownership is reviewed by a trusted platform operator. Add verified email/phone and self-service recovery before an unattended large-scale launch.
- Demo seeding is restricted to development and an empty database.

## Inventory

Each bed belongs to one property and has a room identifier, bed label, sharing count and availability flag. The displayed vacancy count is derived from active beds without an active tenancy. A database partial unique index allows only one active tenancy per bed and one per person. Assignment also locks the request and bed in PostgreSQL. Duplicate room/bed labels are rejected.

Disabled occupied beds are rejected. Checkout releases the bed and removes active tenant access, while preserving invoice history. Current inventory represents occupancy now; future-dated reservations, holds, waitlists and cancellation/refund workflows are outside this release.

## Payments

Amounts are integer paise. Owners issue an invoice for an active tenancy and month; duplicate tenancy/month invoices are rejected. Checkout creates/reuses a provider order while holding an invoice row lock. A provider timeout before the order ID is persisted can leave an orphan unpaid provider order; do not infer payment success from order creation.

The verify route authenticates the tenant, verifies HMAC over the server-known order and payment IDs, fetches payment details server-side, and validates captured status, amount, currency and order. The webhook validates HMAC over the unmodified raw request bytes. Duplicate events are recorded idempotently; payment IDs are unique. Only captured payments unlock receipts.

Gateway settlement, chargebacks, partial payments, credit notes, manual receipts and refunds are not automated here. Reconcile gateway captures and settlements operationally. One property/merchant is intentionally enabled at a time until marketplace payouts are integrated and approved.

## Notifications

Announcement creation and push outbox inserts happen in the same transaction. Multiple worker instances can use PostgreSQL SKIP LOCKED. Deliveries retry up to five attempts; 404/410 endpoints fail immediately. Recheck active tenancy before delivery. Delivery is at least once; client notification tags suppress duplicate visible notices where the browser supports it. Inspect failed jobs and remove stale subscriptions operationally. Push credentials must remain stable across deployments.

## Media and availability

The first release uses one persistent local media volume and a single API deployment. A multi-node deployment needs shared object storage and a CDN before horizontal scaling. Do not deploy uploaded media to an ephemeral filesystem. Photos are public listing media; no tenant identity-document upload endpoint is included.

Public discovery currently loads up to 500 published properties and filters locally, suitable for a bounded pilot. Add server-side pagination, geo indexes, query limits and search ranking before a large marketplace rollout. No fabricated reviews are generated by the connected app.
